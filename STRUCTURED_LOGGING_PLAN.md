# Implementation Plan: Structured HTTP Request Logging

## Goal

Enrich backend logs to emit a structured, machine-readable `http.request.completed` event on every response, including correlation identity, user identity, route/status/duration, runtime metadata, and machine-friendly event names — while respecting UK/EU GDPR constraints on personal data in logs.

---

## Current State

| Area                            | Current behaviour                                                                                                                                                                                                                      |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Request ID**                  | Not generated. `genReqId` is not configured in `createFastifyApp()`. No `requestId` field appears in any log.                                                                                                                          |
| **Response hook**               | No `onRequest` / `onResponse` / `addHook` lifecycle hooks exist anywhere.                                                                                                                                                              |
| **`LoggerPort`**                | 4-method interface (`info`, `warn`, `error`, `debug`). No `child()` / per-request context support.                                                                                                                                     |
| **`PinoLoggerService`**         | Single shared Pino instance injected into every controller and use case at startup. No per-request child logger.                                                                                                                       |
| **Log fields today**            | Free-text `message` + an optional untyped `context` object. Fields are ad-hoc; no `event`, no `requestId`, no `durationMs`, no `route`.                                                                                                |
| **Fastify built-in serializer** | Configured in `createFastifyApp()` — logs `method`, `url`, `headers`, `hostname`, `remoteAddress`, `remotePort` at request/response time via Fastify's own logger (not `PinoLoggerService`).                                           |
| **PII in logs**                 | `remoteAddress` (full IP) is emitted by Fastify's built-in serializer. Emails and tokens are not explicitly excluded at the logger level (though the auth token is redacted from `req.headers.authorization` via the `redact` option). |

## Fields Reference

### Group 1 — Correlation + request identity

| Field        | Source                                                    | Notes                                                                                                       |
| ------------ | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `requestId`  | Generated by Fastify `genReqId` on every incoming request | Use UUIDv7 for time-ordered, k-sortable IDs; Fastify stores it as `request.id`                              |
| `method`     | `request.method`                                          | GET / POST / PUT / DELETE etc.                                                                              |
| `route`      | `request.routeOptions.url`                                | Parameterised path e.g. `/ai/chats/:userId`, **not** the resolved URL — avoids leaking IDs into log indexes |
| `statusCode` | `reply.statusCode`                                        | Read in the `onResponse` hook after the reply is sent                                                       |
| `durationMs` | `Date.now() - request.startTime`                          | `request.startTime` set in `onRequest` hook; round to integer                                               |

### Group 2 — User identity

| Field    | Source                                        | Notes                                                                    |
| -------- | --------------------------------------------- | ------------------------------------------------------------------------ |
| `userId` | `request.user?.sub` (set by `authMiddleware`) | Internal UUID — safe to log. **Never log email, name, or phone number.** |

`tenantId`/`orgId` are not applicable to this codebase today (single-tenant). Add them if multi-tenancy is introduced.

### Group 3 — Runtime / service metadata

| Field     | Source                                                             | Notes                                                                         |
| --------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `service` | `EnvConfig.SERVICE_NAME` (new) or hardcoded string                 | Identifies the service in a multi-service log aggregator (e.g. Loki, Datadog) |
| `env`     | `EnvConfig.NODE_ENV`                                               | `production` / `staging` / `development`                                      |
| `version` | `EnvConfig.APP_VERSION` (new, read from `package.json` or env var) | Helps correlate log spikes with deployments                                   |

### Group 4 — Event names

Replace free-text `message` strings with a stable, machine-friendly `event` field alongside the human message. Use dot-separated namespacing:

| Event                                       | When                                                         |
| ------------------------------------------- | ------------------------------------------------------------ |
| `http.request.completed`                    | Every successful response (2xx / 3xx / 4xx)                  |
| `http.request.error`                        | 5xx or unhandled exception                                   |
| `user.login.success`                        | In `LoginUserUseCase` after token generation                 |
| `user.login.failed`                         | In `LoginUserUseCase` after bad credentials                  |
| `user.registered`                           | In `RegisterUserUseCase` after creation                      |
| `chat.created`                              | In `SaveChatUseCase` after first insert                      |
| `chat.appended`                             | In `AppendedChatUseCase` after message append                |
| `token.refreshed`                           | In `RefreshAccessTokenUseCase` (add `event` field in Step 7) |
| `db.query.failed`                           | On `DrizzleQueryError` in any repository                     |
| `ai.stream.started` / `ai.stream.completed` | Around `streamText` in `AIController.chat()`                 |

### Group 5 — Error details

| Field       | Source                                                           | Notes                                                                                  |
| ----------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `err`       | Pass the `Error` object to Pino as `{ err }`                     | Pino's built-in `err` serializer extracts `type`, `message`, and `stack` automatically |
| `errorCode` | Your `BaseException.code` (e.g. `UNAUTHORIZED`, `TOKEN_EXPIRED`) | Stable code for alerting rules; do not use HTTP status codes as error codes            |
| `cause`     | `error.cause` if chained                                         | Only log if present; avoids undefined noise                                            |

### Group 6 — IP address (GDPR consideration)

Under UK GDPR, a full IP address is personal data. Options:

| Approach                              | Trade-off                                                                                                                                                                 |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Do not log IP in application logs** | Safest. Rely on the infrastructure layer (nginx/CDN/load balancer) access logs for IP, which can be subject to separate, shorter retention.                               |
| **Truncate before logging**           | IPv4: mask the last octet (`192.168.1.x`). IPv6: mask the last 80 bits. Reduces precision enough to remove the "individual identifiable" threshold in most threat models. |
| **Log only in audit logs**            | Keep IP exclusively in the `audit_log` table (already present in this codebase) under a separate, documented retention policy.                                            |

**Recommendation for this codebase:** Remove `remoteAddress` from the Fastify built-in request serializer in `createFastifyApp()` and keep it only in the `audit_log` table where it already exists. If you need it for abuse/security analysis, store only the truncated form.

## Implementation Steps

### Step 1 — Add `genReqId` to Fastify config

**File:** `apps/backend/src/infrastructure/http/fastify.config.ts`

Fastify's `genReqId` option is called once per incoming request and sets `request.id`. Using UUIDv7 (already used elsewhere in the project) gives time-ordered IDs.

```typescript
import { uuidv7 } from 'uuidv7' // already a project dependency

export function createFastifyApp(options?: FastifyServerOptions): FastifyInstance {
  const fastify = Fastify({
    genReqId: () => uuidv7(),
    logger: {
      redact: ['req.headers.authorization'],
      level: EnvConfig.LOG_LEVEL,
      // ... existing serializer config
    },
    ...options,
  })
  // ...
}
```

`request.id` is then available in every handler and hook as `request.id`.

---

### Step 2 — Update `LoggerPort` to support `child()` loggers

**File:** `apps/backend/src/application/ports/logger.port.ts`

Add a `child()` method that creates a new logger pre-bound with a set of fixed fields (e.g. `requestId`, `userId`). This matches Pino's native `logger.child({ requestId })` API.

```typescript
export interface LoggerPort {
  info(message: string, context?: Record<string, any>): void
  error(message: string, error?: Error, context?: Record<string, any>): void
  warn(message: string, context?: Record<string, any>): void
  debug(message: string, context?: Record<string, any>): void
  /** Return a new logger with the given fields pre-merged into every log line. */
  child(bindings: Record<string, any>): LoggerPort
}
```

---

### Step 3 — Implement `child()` in `PinoLoggerService`

**File:** `apps/backend/src/adapters/secondary/services/logger.service.ts`

Pino supports `logger.child(bindings)` natively — it returns a new Pino instance with the bindings merged into every log record at zero serialisation cost (bindings are only serialised once, not per-log-call).

```typescript
child(bindings: Record<string, any>): LoggerPort {
  const childPino = this.logger.child(bindings)
  // Return a new PinoLoggerService that wraps the child Pino instance
  // The simplest approach: expose a private constructor or factory that
  // accepts an existing pino.Logger instead of creating one.
  return new PinoLoggerService(childPino)
}
```

Add a second constructor overload (or a private factory method) that accepts a `pino.Logger` instance directly, so `child()` can return a properly-typed `PinoLoggerService`.

### Step 4 — Add static service-level fields to the Pino base config

**File:** `apps/backend/src/adapters/secondary/services/logger.service.ts`

Pino supports a `base` option that merges fixed fields into every log line — ideal for `service`, `env`, and `version` which never change at runtime.

```typescript
this.logger = pino({
  level: EnvConfig.LOG_LEVEL,
  base: {
    service: EnvConfig.SERVICE_NAME, // new env var
    env: EnvConfig.NODE_ENV,
    version: EnvConfig.APP_VERSION, // new env var
  },
  // ... rest of options
})
```

This means every log line — including those from use cases — will carry `service`, `env`, and `version` without any per-call overhead.

### Step 5 — Register `onRequest` and `onResponse` Fastify lifecycle hooks

**File:** `apps/backend/src/infrastructure/http/fastify.config.ts`

These hooks are the right place for the `http.request.completed` log because they fire at the HTTP boundary — outside of controllers — and have access to the full timing, route, and reply data.

```typescript
// In createFastifyApp(), after plugin registrations:

fastify.addHook('onRequest', (request, _reply, done) => {
  // Attach request start time for duration calculation
  request.startTime = Date.now()
  done()
})

fastify.addHook('onResponse', (request, reply, done) => {
  // Skip logging here for server errors — onError already emitted http.request.error for those
  if (reply.statusCode >= 500) {
    done()
    return
  }

  const durationMs = request.startTime != null ? Math.round(Date.now() - request.startTime) : -1
  const userId = request.user?.sub ?? undefined

  request.log.info(
    {
      event: 'http.request.completed',
      requestId: request.id,
      userId,
      method: request.method,
      route: request.routeOptions?.url ?? request.url,
      statusCode: reply.statusCode,
      durationMs,
    },
    'request completed'
  )

  done()
})

fastify.addHook('onError', (request, reply, error, done) => {
  const durationMs = request.startTime != null ? Math.round(Date.now() - request.startTime) : -1

  request.log.error(
    {
      event: 'http.request.error',
      requestId: request.id,
      userId: request.user?.sub ?? undefined,
      method: request.method,
      route: request.routeOptions?.url ?? request.url,
      statusCode: reply.statusCode,
      durationMs,
      errorCode: error instanceof BaseException ? error.code : 'INTERNAL_ERROR',
      err: error,
    },
    'request error'
  )

  done()
})
```

Note that `request.log` is Fastify's **built-in per-request Pino logger** — it automatically carries `reqId` (Fastify's internal name for `request.id`). The fields you pass in the `onResponse` hook merge with this context.

You will need to augment the `FastifyRequest` type to include `startTime`:

```typescript
// In apps/backend/src/shared/types/fastify.d.ts (existing file — add to the existing interface)
import 'fastify'

declare module 'fastify' {
  interface FastifyRequest {
    startTime?: number
  }
}
```

### Step 6 — Per-request child loggers in controllers (optional but recommended)

The `onRequest` / `onResponse` hooks (Step 5) cover the HTTP boundary log with no controller changes. However, to get `requestId` and `userId` into **use-case-level** logs (e.g. `user.login.success`, `chat.created`), you need per-request child loggers.

The pattern:

```typescript
// In a controller handler (e.g. AIController.chat):
async chat(request: FastifyRequest, reply: FastifyReply) {
  const reqLogger = this.logger.child({
    requestId: request.id,
    userId: request.user?.sub,
    event: 'ai.stream.started',
  })
  // Pass reqLogger to the use case instead of this.logger
  await this.saveChatUseCase.execute(chatId, userId, messages, auditContext, reqLogger)
}
```

This requires adding an optional `logger?: LoggerPort` parameter to use-case `execute()` methods — or passing it via a request context object. The simpler approach is to keep use-case loggers for business events and rely on the hook-based HTTP boundary log for correlation.

**Trade-off table:**

| Approach                                   | Pros                                                 | Cons                                                               |
| ------------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------------ |
| Hook-only (Step 5 alone)                   | Zero changes to controllers or use cases             | `requestId` only appears on the boundary log, not on use-case logs |
| Per-request child logger                   | `requestId` in every log line for a request          | Requires passing a logger down through use cases                   |
| Request-scoped DI (e.g. AsyncLocalStorage) | `requestId` everywhere without passing it explicitly | More complex infrastructure change                                 |

For this codebase, **hook-only is the recommended starting point**. Per-request child loggers can be added incrementally to high-value use cases (login, chat creation).

### Step 9 — Fix the Fastify built-in serializer for GDPR compliance

**File:** `apps/backend/src/infrastructure/http/fastify.config.ts`

Remove `remoteAddress` and `remotePort` from the built-in request serializer. These are already captured in the `audit_log` table where they belong.

```typescript
serializers: {
  req(req) {
    return {
      method: req.method,
      url:    req.url,
      // remoteAddress and remotePort intentionally omitted — IP is PII under UK GDPR.
      // IP is retained in the audit_log table under a separate retention policy.
    }
  },
},
```

The `req.headers` field should also be removed or heavily redacted from the default serializer — it can contain `Cookie`, `Authorization`, and other sensitive values. The `redact: ['req.headers.authorization']` option only redacts one field; it does not prevent all headers from being logged by Fastify's own request log.

```typescript
serializers: {
  req(req) {
    return {
      method: req.method,
      url:    req.url,
      // Headers intentionally omitted — may contain cookies, auth tokens, and other PII.
      // Authorization header is already redacted but removing the entire headers object
      // is safer and reduces log volume.
    }
  },
},
```

### Step 10 — Audit existing log call sites for PII

Do a project-wide search for the following patterns and audit each result:

| Pattern to search for                           | Risk                                       |
| ----------------------------------------------- | ------------------------------------------ |
| `email` inside a `logger.` call                 | Email is PII — remove or hash              |
| `req.headers` inside a `logger.` call           | May leak auth tokens or cookies            |
| `password` inside a `logger.` call              | Critical — must be removed                 |
| `token` inside a `logger.` call                 | Access/refresh tokens must never be logged |
| `ip` or `remoteAddress` inside a `logger.` call | IP is PII under UK GDPR                    |

The `apps/backend/src/domain/audit/redact-sensitive-data.ts` module defines a `SENSITIVE_FIELDS` constant listing sensitive field names to redact in audit logs. The same list should inform a Pino `redact` configuration:

```typescript
this.logger = pino({
  redact: {
    paths: ['email', 'password', 'token', 'accessToken', 'refreshToken', 'resetToken', 'ip'],
    censor: '[REDACTED]',
  },
  // ...
})
```

## Suggested Implementation Order

1. `genReqId` in Fastify config (smallest, zero risk)
2. New env vars (`SERVICE_NAME`, `APP_VERSION`)
3. `base` fields and `redact` in `PinoLoggerService`
4. `onRequest` / `onResponse` / `onError` hooks + `FastifyRequest` type augmentation
5. Fix Fastify built-in serializer (remove PII)
6. `child()` on `LoggerPort` and `PinoLoggerService`
7. Audit and update use-case log call sites (`event` fields, remove PII)
8. Update/add tests
